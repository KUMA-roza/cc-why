ログに「なぜ」はほぼ残っていない。だから、残っている手がかりから推定し、根拠の強さを添えて見せる

結論: Claude Code の会話ログ (JSONL) から、ツール呼び出し 1 回ごとに「なぜそうしたか」を推定する CLI cc-why を作る。ツール呼び出しの 64% には本人の言葉 (thinking・直前の説明文・Bash の説明) が残っていないので、推定には必ず「根拠の強さ」と「指示元 (どの SKILL.md / CLAUDE.md の何行目がそうさせたか)」を付ける。ハーネスを直す材料になるのは、この指示元と、「読んだのに後で使わなかったファイル」の 2 つ。
このシートで使う言葉:
・ログ — ~/.claude/projects/<プロジェクト>/<セッション>.jsonl。1 行 1 イベントの会話記録。subagent の分は <セッション>/subagents/ に別ファイル
・セッション — Claude Code を 1 回起動してから終えるまでの会話。ログ 1 本に当たる。8 桁の英数字は ID の先頭
・ステップ — ツール呼び出し 1 回 (Read 1 回、Bash 1 回…)。分析の 1 行の単位
・推定 — 後から LLM にログを読ませて「この時点でこう考えたはず」と推し量ること。本人の言葉ではない
・未使用 — 読んだファイルの名前・中身が、その後の説明文にもツールの入力にも一度も現れないこと (LLM を使わず機械的に判定)
・claude -p — Claude Code を画面なしで 1 回だけ動かし、答えを標準出力に返す起動方法
・attributionSkill — ログの各行に Claude Code が付ける「どの skill の最中か」の欄
・指示元 — そのステップを促した文書の行。例: SKILL.md の「手順 3: rubric を Read」
・ハーネス — Claude Code を動かす周りの設定一式 (CLAUDE.md・skill・hook・設定ファイル)

ログに残る手がかりは 4 種類。どれも欠けがちなので、強さを明示する

手元のログ 28 本 (セッション 15 本 + subagent 13 本) を数えると、ツール呼び出し 517 回のうち、本人の言葉が添っていたのは 188 回 (36%)。内訳を見ると thinking はほぼ空で、中身が読めたのは 284 個中 10 個だけ。ログの各行には "thinkingDisplay":"updates" と記録されていて、要約表示の設定では中身を保存しないと見られる (設定との関係はまだ確かめていない)。

そこで推定には 根拠の強さ 3 段階 を必ず付ける。強 = 本人の言葉 (thinking・直前の本文・Bash の説明) がある。中 = 直前の結果や SKILL.md の文に「これを読め」とある。弱 = 流れからの推測だけ。ハーネスを直す判断は「強・中」だけで行い、「弱」は参考に留める。

下は、実際のログ (cognitive-ease-html の skill を使った 10/31 のセッション) の 5 ステップを、このツールで見るとどうなるかの再現。時刻・ツール・対象ファイルは実ログのまま。推定文・根拠・指示元・⚑ は説明用の例。

決めてほしいこと (3 問 — 未回答は推奨で進める)

問 1. 「なぜ」の出どころを、過去ログからの推定だけにするか、今後のログに本人の言葉を足すか

  • A. 推定だけ (過去ログ 28 本をそのまま使う)推奨 — 利点: 今すぐ全ログで動き、Claude の振る舞いを一切変えない。代償: 本人の言葉は 36% だけで、残り 64% は推し量った理由になる。
  • B. 推定 + 今後は CLAUDE.md で「ツールの前に意図を 1 行書く」と指示 — 利点: これからのログは根拠「強」がほぼ全ステップに付く。代償: 書かせる指示そのものが Claude の動き方を変えるので、「普段の動き」の分析ではなくなる。ターミナルの出力が毎回 1 行増える。

根拠: 実行結果 — ~/.claude/projects/*/*.jsonl と */*/subagents/*.jsonl を python で走査し、type=assistant の行のツール呼び出しを数えた: 517 回中、前に本人の言葉あり 188 回 (36%)。Bash 256 回中、引数 description (コマンドの説明) あり 158 回。hook はツールの入力しか受け取れず、理由を書き足せるのは Claude 自身だけなので、足す手段は CLAUDE.md の指示になる。

問 2. レポートは、1 セッションを順に追う形か、全セッションを束ねた集計か

  • A. タイムラインを先に作り、集計は次の段階推奨 — 利点: 推定が正しいかを人が 1 行ずつ確かめられる。推定の質が見えてから集計に進める。代償: 「どこを直すと一番効くか」は人が複数セッションを見比べて探す。
  • B. 集計を先に作る — 利点: 28 本を一度に見て、繰り返し起きる無駄 (同じ指示元で何度も未使用) がすぐ順位で出る。代償: 推定が間違っていても数字に埋もれて気付きにくい。

根拠: 実行結果 — 同じ走査で、ログの行を attributionSkill の値ごとに数えた: run-workshop-deck 175 行 / akapen 45 / cognitive-ease-html 27 / html-plan 24。1 skill でログが数十〜百数十行になるので、タイムラインは skill で絞り込める形にする。

問 3. 推定に使う LLM をどう呼ぶか

  • A. claude -p (ヘッドレスの Claude Code) を呼ぶ推奨 — 利点: API キー不要で、今使っている Claude のプランのまま動く。使うモデルも Claude Code の設定に従う。代償: 1 セッションずつ順に回すので、28 本全部だと数十分かかる見込み。推定を走らせた分も新しいログとして残るので、cc-why が自分の実行を見分けて分析から外す。
  • B. Anthropic API を直接呼ぶ (ANTHROPIC_API_KEY) — 利点: 並列に回せて、28 本でも数分。失敗時の再実行や出力の検査を細かく制御しやすい。代償: API キーと使った分の課金が別に要る。
  • C. LLM を使わない (抽出した手がかりを並べるだけ) — 利点: 無料・一瞬・毎回同じ結果。「強」の根拠はそのまま読める。代償: 本人の言葉の無い 64% のステップは「なぜ」が空欄のまま。人が読んで推し量る。

根拠: ログ全体は du -sh ~/.claude/projects = 103M。1 本最大 12MB (33126d3e-6636-4a33-a596-b429bcd8b6d1.jsonl) で、そのまま LLM に入らない。抽出で手がかりだけに絞ってから渡す前提。

落とした案 2 つと、作り方の前提 (箇条 6 行)

・落とした案: hook (ツール実行前に動くもの) で毎回理由を記録 — hook はツールの入力しか見えず、Claude の理由は受け取れない。

# cognitive-ease-html — 頭が疲れない 1 枚の HTML 図解

材料 (調べた事実・作業の結果・データ) を、読む人が **30 秒で「何の話で、結論は何か」をつかめる** 1 枚の HTML にする。

- **入力**: テーマと材料。実名・実数は材料からだけ取る
- **出力** (既定の出力フォルダ = `./cognitive-ease/<日付>-<短い題>/`):
  - `out-shared.html` — 画像まで埋め込んだ自己完結の 1 枚。**人に渡すのはこれ**
  - `out.html` / `design.json` / `content.json` / 図の SVG / `coldread.json` (読み手チェックの結果)
- **要るもの**: Node.js 18 以上 (`node -v` で確かめる。無ければユーザーに入れてもらう — 紙面は必ず render.js で組むので、node 無しで手書きしない)

このファイルのパス表記 `<skill>` は、この SKILL.md が置かれたフォルダ (例 `~/.claude/skills/cognitive-ease-html`)。

## 守ること (先に読む)

1. **事実を作らない** — 名前・数字・日付は材料にある物だけ。足りない数字は作らずユーザーに聞く
2. **HTML を手で書かない** — 紙面は `content.json` を `scripts/render.js` に通して作る。render.js のエラーは content.json 側を直して消す (テンプレと render.js は変えない)
3. **材料の箇条書きをそのまま節にしない** — 節の立て方は「読む人に持ち帰ってほしい 1 文」から決める
4. **作業の言葉を紙面に持ち込まない** — このファイルの言葉 (design.json・takeaway・手順番号など) や、会話の中だけの呼び名・略語は、読む人の普段の言葉に直す
5. **自分で点を付けない** — 分かりやすさの判定は、手順 5 の「文脈を知らない読み手」に任せる

## 手順 1: 伝え方を決める (design.json)

書き始める前に、出力フォルダへ `design.json` を書く (形は `assets/design.schema.json`)。

- `reader` — 誰が読むか (1 行。例「この作業を頼んだ人。細かい経緯は覚えていない」)
- `reader_knows` — 読む人が説明なしで分かる言葉 0〜3 個。ここに無い専門語・内輪の言葉は、本文で 1 行説明してからでないと使わない
- `takeaway` — 読む人に持ち帰ってほしい 1 文 (このページがある理由)
- `support` — takeaway を支える事実 3 つまで
- `subject_anchor` — 何の話かを示す固有名 (サービス名・ファイル名・店名など)。上の小見出し・タイトル・冒頭の図のどれにも必ず出す
- `avoid_terms` (任意) — 読む人に見せない語 (社内のコードネーム等)

読む人がはっきりしない時だけ、ユーザーに 1 行で確かめる。

## 手順 2: 中身を書く (content.json)

形は `assets/content.schema.json`、見本は `assets/content.sample.json`。

- `kicker` (タイトル上の小見出し) / `title` (takeaway の言い換え) / `conclusion` (結論の本文。「結論:」はテンプレが付けるので書かない) / `three_lines` (ちょうど 3 本、support から) / `sections` (3〜5 個。各節 = 主張 1 つ + 段落 1〜3 + 図) / `meta` (date = 今日の日付、source = 材料の出所)
- 節を入れるかは「takeaway を支えるか」で決める。材料にあるから、では入れない
- 主な数字は conclusion か three_lines に `**太字**` で入れて、最初の 1 画面で見えるようにする
- 持ち帰りの 1 文は `callout`、強調は `**太字**`。色や装飾は足さない

**文章のきまり** (詳しくは `assets/writing-rubric.md` — 書く前に一度読む):

- 1 文は 80 字以内 (render.js が検査)。1 段落は 2〜4 文・200 字まで
- 使ってよい言葉は 3 種だけ: 普通の言葉 / reader_knows の言葉 / 本文で初めて出す時に 1 行で説明した言葉
- 読む人が知っている物を比喩に置き換えない
- 「〜ではない。〜だ」の言い回し、「理由は〜にある」型の決まり文句、言い直しのまとめ文を書かない
- 大事な「なぜそうなるか」は省かない
- タイトルは、数字や固有名の入った事実の言い切りにする (「X — Y」の副題型・抽象語の体言止めにしない)
- kicker は「題名 + レポート」のような埋め草にしない。このページの性格 (実測なのか・不具合の調べなのか・入門なのか) を書く
- カードの見出しは体言止め・25 字以内。節見出しの上にラベルや番号を置かない

## 手順 3: 図を作る

- **冒頭の図 (hero)** — takeaway を 1 枚の絵にした SVG。出力フォルダに `hero.svg` を書き、content.json の `hero.src` で指す。要素には短い日本語ラベルを付け、矢印で関係を示す。数字は描き込まない。章立ての地図にしない。実際の画面のスクショなど本物の画像があれば、そちらを優先して hero に置く
  - hero.svg は別ファイルなので色の変数が効かない。色はこの 9 色の hex だけ: `#212529` `#64707C` `#DEE2E6` `#FFFFFF` `#F6F8FA` `#2563EB` `#16A34A` `#D97706` `#DC2626`
- **各節の図** — どの節も図を付けるのが基本。数字の比較・推移・割合はチャート (実数のラベル付き)、仕組みや流れは図。content.json の `sections[].svg` に `<svg>` をそのまま入れる。後で値を引く表 (単価・対応表など) だけ `sections[].table`
- 節の図の決まり (render.js が検査する):
  - `xmlns="http://www.w3.org/2000/svg"`・`viewBox`・`role="img"`・`aria-label` を付ける
  - 色は変数だけ: `var(--ink)` `var(--muted)` `var(--line)` `var(--paper)` `var(--paper-dim)` `var(--accent)` `var(--ok)` `var(--warn)` `var(--err)`。hex を直接書かない
  - 塗りつぶしに `var(--ink)` を使わない (黒い面になる。ink は文字と線だけ)
  - opacity は 1 / 0.6 / 0.35 / 0 だけ。等幅フォントに太字 700 を使わない
  - 異常な値だけ `var(--err)`。ラベルは省略しない言葉で、文字は 9.5〜12.5px
  - 箱の中の文字は 2 行まで。手順が 6 個を超えたら段階ごとにまとめる
- Agent ツールが使えるなら、節ごとに図を別の subagent へ並べて頼むと速い (上の決まりをそのまま渡す)。使えなければ自分で順に描く

## 手順 4: 組む

```bash
node <skill>/scripts/render.js content.json -o out.html
```

エラーが出たら content.json を直して、通るまで繰り返す。ブラウザで撮れる道具 (ヘッドレスの Chrome / Edge、Playwright など) があれば 1 回開いて崩れを見る。無ければ「見た目は未確認」と報告に書く。

## 手順 5: 文脈を知らない読み手に読ませる

Agent ツールで新しい subagent を 1 体立て、**out.html だけ** を渡す (作業の経緯・design.json・このページの説明は一切渡さない。渡すと甘くなる)。渡す前に、テーマ名の入っていないフォルダへコピーし、`<details>` で畳んだ部分は消しておく。頼む文:

> このファイルを 1 回だけ読んでください (読み返さない)。答えてほしいこと: ① 何の話か ② 誰向けか ③ 一番言いたいことを 1 文で ④ 主な主張 3 つについて、なぜそうなるのかをページの言葉だけで ⑤ 普段使わない言葉・造語・内輪の言葉だと感じた語を全部

答えと design.json を自分で突き合わせ、次のどれかに当たれば直す:

- ① に subject_anchor (かそれと分かる物) が出ない / ③ が takeaway と意味で一致しない
- ④ の「なぜ」がページの言葉で 2 つ以上組み立てられていない
- ⑤ に、reader_knows にもページ内の説明にも無い語が 3 つ以上ある

直したら手順 4 → 5 をもう 1 回だけ。それでも当たる時は、そのまま進めて報告に書く。結果は `coldread.json` (読み手の答え・判定・引っかかった語) に残す。Agent ツールが無い環境では、この手順を飛ばしたと報告に書く。

## 手順 6: 共有版を作って開く

```bash
node <skill>/scripts/inline-assets.js out.html   # → out-shared.html (画像を埋め込む)
```

`out-shared.html` をブラウザで開く (macOS `open` / Windows `start ""` / Linux `xdg-open`。開けなければパスを伝える)。チャットの返事は短く: 1 行目に結論、次にファイルの場所、読み手チェックの結果 (直した回数・残った引っかかり語)。人に渡す・PDF にする時も、必ず `out-shared.html` を使う (out.html は画像が別ファイルなので単体では欠ける)。

## つまずきやすい所

- 図が黒くなる: 変数にない色名 / hero.svg で変数を使った / 塗りに `var(--ink)`。どれも render.js が止めるので、エラー文に従って直す
- 冒頭に数字のカードを並べない。冒頭は hero の図。`kpis` は数字が主役のダッシュボード型のページだけ
- hero を飾りのアイコン並べにしない — ラベル付きで、takeaway を 1 枚で言える図にする
- 数字だらけの補足は段落に並べず `appendix.table` へ
- 材料の文体・作業の言葉は、生成した側には読めても人には読めない。手順 5 の ⑤ が頼り
